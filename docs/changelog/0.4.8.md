# [0.4.8] — 2026-10-15

All 5 fixes in this release were filed the same day — someone verified the freshly-published 0.4.7
Maven Central artifacts against the real kandraorm.com quickstart/tutorial and found 5 real bugs
(GH #152–#156). The website already carried workarounds for some of these; this release fixes the
library itself.

### Fixed

- **Integration modules published `kandra-core`/`kandra-runtime` at `runtime` scope instead of
  `compile`** — a consumer depending on `kandra-ktor` alone couldn't compile against
  `io.kandra.core.annotations.*`, `KandraAuth`, or `io.kandra.runtime.repository.*` without adding
  `kandra-core`/`kandra-runtime` explicitly. Changed the affected modules'
  (`kandra-runtime`/`-ktor`/`-koin`/`-kodein`/`-test`/`-migrate`/`-jakarta`) Gradle dependencies from
  `implementation` to `api` wherever that module's own public API exposes another module's types,
  matching `kandra-multidc`'s existing pattern (GH #152 / ISS-100).
- **`@SoftDelete`'s marker column, written without a TTL, left a permanent key+marker husk row** —
  added `markerTtlSeconds` (defaulting to `ttlSeconds + gcGraceSeconds`), and — found only by
  testing against a real cluster, not unit tests — fixed the marker write itself to be an `INSERT`
  under that TTL rather than an `UPDATE`, since the row's original `save()` `INSERT` leaves a
  permanent, untouchable-by-`UPDATE` row-marker cell that the marker-only fix didn't account for
  (GH #154 / ISS-097).
- **`@SoftDelete` reads threw once a deleted row's TTL expired, if any property was non-nullable**
  — `SchemaRegistry.register()` now rejects a `@SoftDelete` entity at registration time if any
  persisted, non-key, non-marker property is non-nullable with no constructor default (GH #153 /
  ISS-098).
- **`kandra-codegen` emitted an invalid empty `package` line for entities in the default package**
  — fixed to omit the `package` line entirely rather than emit it empty (GH #156 / ISS-099).
- **No documented supported Ktor version range** — `README.md` and `kandra-ktor`'s plugin KDoc now
  state "built and tested against Ktor 2.3.x; Ktor 3.x untested." The other half of this issue (a
  real CI job testing against Ktor 3.x) is split out to GH #160, since Ktor 3 restructured parts of
  the plugin-installation API — a genuine compatibility pass, not a doc fix (GH #155 / ISS-101).

### Documentation

- Audited `docs/issues/README.md` against GitHub's actual issue state: the 2026-09-09 post-fix
  critical-audit batch (ISS-080–ISS-096, GH #93–#109) had sat listed as `Open` for over a month
  after every one of those GH issues had actually been closed. Moved to `Fixed`, with each
  individual file's own `Status:` line corrected too.
- Fixed `README.md`'s own Tombstone-Aware Soft Delete example, which would have failed registration
  under this release's new `@SoftDelete` nullability guard.
- Added `docs/issues/ISS-097`–`ISS-101`, one per fix above.

### Testing

- `SchemaRegistrySoftDeleteTtlTest` (kandra-core): the marker-TTL resolution formula and the
  non-nullable-column registration guard.
- `SoftDeleteMarkerTtlLiveClusterTest` (kandra-runtime, `@Tag("manual")`): connects directly to a
  real local cluster and soft-deletes a row with short TTLs — this is what caught the row-marker
  gap in GH #154's fix above; the marker-column-TTL-only version passed every unit test while still
  leaving a permanent husk on a real cluster.
- `KandraProcessorDefaultPackageTest` (kandra-codegen): compiles a real default-package entity
  through the actual KSP processor.
- Full project test suite (`./gradlew test`, all 11 modules) run locally against a real cluster
  before every merge in this release.
